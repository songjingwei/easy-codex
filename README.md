# easy-codex

从一句需求，到经过审查和验收的功能。

**easy-codex 希望让开发者更简单地开发功能。** 它计划基于 [Pi Durable](https://earendil.com/posts/pi-durable/) 构建一个开发 Agent，将需求澄清、产品规格、UI/UX 设计、技术规划、实现、验收和复盘串成一套可恢复、有人参与决策的工作流。

## 为什么做 easy-codex？

AI 可以写代码，但交付一个功能不只是写代码。开发者仍然需要不断解释需求、协调不同工具、检查设计、追踪实现进度，并判断结果是否符合预期。

easy-codex 希望承担这些衔接工作，让开发者专注于关键决策：

- 我们真正要解决什么问题？
- 需求和设计是否符合预期？
- 实现结果是否可以接受？

它的目标不是绕过人的判断，而是让 Agent 负责推进工作，在关键节点等待用户确认。

## 目标工作流

### 1. 澄清需求

用户输入需求文案，Agent 参考 `grill-with-docs` 的方式，结合项目文档与代码追问，明确目标、使用场景、范围、非目标和待决问题。

**确认点：用户认可需求理解。**

### 2. 生成 PRD 与 Spec

使用 `to-spec` 等能力，将对齐后的需求整理成 PRD 和可执行的规格，明确行为规则、边界情况与验收标准。

**确认点：用户认可需求范围与预期行为。**

### 3. 设计 UI/UX

对于涉及界面的需求，计划结合 [Impeccable](https://impeccable.style/) 的设计能力，产出可供用户 review 的设计或交互原型。用户可以提出意见，Agent 据此迭代。

不涉及界面的需求可以明确跳过本阶段；存在重大技术约束时，应先检查可行性。

**确认点：用户批准当前版本的设计。**

### 4. 拆分 Tickets 与技术方案

依据已确认的 PRD、Spec 和设计，使用 `to-tickets` 等能力生成技术方案与可追踪的 tickets，明确依赖关系、实现范围和验收条件。

重大技术决策交由用户确认。

### 5. 实现与自检

使用 `implement` 等能力逐项实现 tickets，运行必要的测试与代码 review，再生成面向用户的验收文档。

验收文档应详细说明：

- 如何准备环境、启动功能和准备测试数据。
- 每个场景的操作步骤与预期结果。
- 需要检查的异常场景与边界情况。
- 已知限制、尚未验证的内容和必要证据。

### 6. 用户验收与调整

用户按验收文档验证功能，并反馈结果：

- **不符合已确认 Spec**：在当前需求内修复。
- **不改变已批准范围的小调整**：在当前流程内处理，并同步相关文档与测试。
- **新增能力或较大的范围变化**：建议用户提交当前代码后，新建需求重新走流程；是否提交由用户决定。

验收调整后，再检查最终代码与文档是否一致。

### 7. Review 与 Retro

结合 code review 和 retro 能力，检查最终变更、整理交付结果，并总结本次开发中值得保留的经验与需要改进的问题。

## Web 入口（Kanban 看板）

```bash
pnpm install
pnpm run web        # 启动 Web 看板，打开 http://localhost:3000
```

- **七列 Kanban**：clarify → spec → design → tickets → implement → accept → retro，当前阶段高亮；已批准列显示 commit 短 SHA、批准时间与该阶段产物路径，未批准显示「未批准」。
- **Web 批准**：当前阶段列的「批准」按钮复用 CLI 的 `--approve` 逻辑——生成 `approved:<phase>` 提交 + memo 并推进阶段，失败时错误原样展示。
- **产物查看**：点击产物路径只读查看 Markdown 原文；请求路径限制在 `specs/`、`tickets/`、`acceptance/` 内，逃逸请求被拒绝。
- **轮询刷新**：每 2s 轮询（`document.hidden` 时暂停），多个浏览器标签附接同一会话、共享同一份磁盘状态。

产物与验收：`specs/web-kanban/`（PRD / Spec / Design）、`acceptance/web-kanban/acceptance.md`。

## 设计方向

### Skills 提供能力，工作流管理推进

Skills 描述如何完成各阶段的工作；easy-codex 负责当前阶段、推进条件、批准记录和变更规则；Pi Durable 提供持久化执行的底座。

```text
用户输入需求、确认方案、反馈验收结果
                  │
             easy-codex
       阶段推进 · 产物关联 · 审批管理
                  │
        Skills / 工具 / 执行环境
                  │
             Pi Durable
       会话 · Tasks · Documents · 恢复
```

阶段转换不应只依赖提示词约定，而应由程序校验必要条件。

### 关键批准与产物版本绑定

“已批准”必须对应明确的需求或设计版本。产物发生实质变更后，需要识别受影响的方案、tickets 与验收项，并重新确认，不能继续沿用旧批准。

### 进度可以恢复，副作用不能盲目重放

计划利用 Pi Durable 的 Tasks、检查点和 Documents 保存执行进度与应用状态，在进程退出后恢复工作。

恢复不意味着无条件重跑。文件修改、Git 操作、数据库迁移和外部服务调用需要根据实际状态核对，必要时使用幂等机制或请求人工确认。数据库中的状态与项目文件也需要进行一致性检查。

### 成果可检查、可追踪

计划将 PRD、Spec、技术方案、tickets 和验收指南保存在项目目录中，便于阅读、版本管理与 review，并建立需求到验收项的关联，而不是只保留在聊天记录里。
