# Easy Codex 项目目标

> 状态：初始草案，持续补充中。
> 本文记录产品目标、已提出的流程与阶段通过条件。尚未确认的规则单独列出，作为后续讨论入口。

## 产品定义

**Easy Codex 首先是完备的项目内 coding agent**：在绑定的 Git 仓库上，为多需求提供独立的上下文与 worktree，按讨论 → 对齐确认 → 影响考察 → 可交互设计稿 → spec/tickets → 实现 → 代码审查 → 有证据验收的流水线推进交付，并支持中断恢复与结果核查。

**桌面端与服务端是同一能力的部署形态**，只决定 Agent harness、工具执行与存储落在何处；不改变阶段定义与通过条件。

**游戏化主界面是交互范式**：用来表达并行需求、待你决策的事项与已验收成果，承载参与感与反馈，不替代 Agent 与流程本身。

## 1. 项目愿景

让开发像游戏一样好玩。用户通过 Agent 协作，在可探索、可互动、会随真实项目成果变化的世界中，完成从提出需求到最终交付的完整流程。

**游戏般的参与感是核心体验目标之一。** 用户应能主动探索项目、作出有意义的决定、与 Agent 协作，并从实际功能的诞生中获得反馈与成就感。主界面采用游戏场景承载需求推进和用户参与；具体玩法通过原型验证后确定。

**并行开发是 Easy Codex 的第一原则。** 用户可以同时提出多个需求，让它们同时进入流程、独立推进；产品从一开始就必须支持多个需求并行讨论、设计、实现、审查和验收。

用户上传 Markdown 需求文档作为起点。Agent 与用户讨论对齐后复述需求，由用户判断 Agent 是否已经理解；随后考察用户对当前需求所影响的现有功能的了解程度，再生成可交互、可供审核的 HTML UI/UX 设计稿。设计稿通过后，Agent 根据需求和设计稿生成存放在项目中的 spec 与 tickets，逐项实现，再由不同模型进行代码审查，并使用 Playwright 等工具完成有证据支持的验收。

各阶段满足通过条件后，才能进入下一阶段；存在问题时继续讨论、修改或修复。当前已明确从需求输入到实现、代码审查和验收的七个阶段；最终交付需要包含实现成果、相关文档及验收证据，具体交付形式仍待明确。

### 游戏体验方向
已确定的目标是让用户愿意参与开发过程，能够理解自己的决定怎样影响项目，并感受到项目持续成长。体验围绕真实需求与真实成果展开，保留现有七步流程和通过条件。

初步体验循环为：**提出一个想法 → 与 Agent 探索和明确目标 → 作出决定 → 体验设计与实现 → 验证成果 → 看到项目世界发生变化 → 开始下一个想法**。

以下为待原型验证的玩法建议，不代表已经确定的产品机制：

- **探索感**：进入项目后能发现正在推进的工作、需要参与的问题和已经实现的能力；场景对象可以直接打开对应内容。
- **创造感**：提出需求像发起一次建设，审核设计时实际体验候选方案，反馈能够影响最终成果。
- **协作感**：Agent 通过可理解的行为与对话呈现当前工作，用户能够介入、调整方向并看到响应。
- **成长感**：已验收的功能为项目留下可回访的成果与场景变化，逐渐形成属于该项目的发展历程。
- **掌控感**：并行需求可随时切换，下一项需要用户作出的决定清楚可见；等待反馈时其他需求继续推进。
- **完成感**：交付时呈现可操作的新功能、前后变化和验收证据，场景反馈与实际交付结果对应。

玩法应让必要决策更易理解，并提供及时反馈。移动、对话演出和庆祝动画支持跳过或简化，不增加强制操作、额外审核阶段或人为等待。考察阶段仍围绕业务理解设计，并保留已规定的通过条件；题目呈现和答题反馈可以探索更有趣的方式。

世界观、美术风格、角色设定、建造或探索的具体操作，以及是否引入收集与装饰机制，均待后续设计。优先用一个完整需求验证参与乐趣，再决定扩展哪些玩法。

### 并行需求与工作空间

- **每个需求独立运行七步流程**：分别保存讨论上下文、确认结果、考察得分、设计稿、spec、tickets、实现进度、审查结果和验收证据，用户可以在多个需求之间切换。
- **不同需求可以处于不同阶段**：例如需求 A 正在实现，需求 B 正在审核设计稿，需求 C 正在讨论；某个需求等待用户回复、修改或处理问题时，不阻塞其他无依赖需求。
- **使用 Git worktree 支持代码隔离**：为并行开发的需求分配独立分支与 worktree，让各需求的 Agent 在各自工作目录中修改、运行和验证代码。
- **产出与运行环境按需求区分**：设计稿、spec、tickets 和验收证据归属于对应需求；并行预览与验收时避免端口、测试数据等相互干扰。
- **明确依赖与集成关系**：有真实依赖的需求按依赖推进，其余需求可并行。Git worktree 隔离工作目录，但合并时仍需处理冲突并验证集成结果；具体集成策略待确定。

以上是贯穿七步的基本能力，不增加额外的用户审核阶段。

## 2. 核心参与者

- **用户／需求提出人**：上传需求文档，参与讨论，确认 Agent 的需求复述，接受理解考察，并审核设计稿。
- **Agent**：阅读需求和相关项目上下文，发起澄清讨论，整理并复述需求，考察用户的理解程度，生成及修改设计稿，编写 spec 与 tickets，执行实现、修复和工具验收，依据阶段结果推进流程。
- **代码审查模型**：使用不同于实现阶段的模型，结合需求、spec、设计稿及项目规范审查实现，给出有依据的审查结果。

## 3. 已明确的工作流程

### 阶段一：上传需求与讨论对齐

**目标**：围绕需求文档进行讨论，使 Agent 与需求提出人对需求形成一致理解。

**输入**：用户上传的 Markdown（`.md`）需求文档，以及项目中与该需求相关的已有上下文。

**主要行为**：

1. Agent 阅读需求文档，识别模糊描述、信息缺口和需要用户决策的问题。
2. Agent 与需求提出人分轮讨论，逐步明确需求的目标、范围、业务规则和关键细节。
3. 涉及已有功能或实现的问题，优先考察项目中的相关资料和代码，再围绕无法自行确定的部分向用户提问。
4. 将讨论中形成的共识记录到文档，供后续复述、考察和设计使用。

**阶段产出**：已澄清的需求内容与讨论结论。

**流转条件**：讨论完成后进入阶段二；若阶段二发现理解存在问题，返回本阶段继续讨论。

**实现参考**：[AI Hero：The grill-with-docs skill](https://www.aihero.dev/skills-grill-with-docs)。

该文章提供的参考思路包括分轮追问、读取代码来回答已有实现问题，以及在澄清过程中及时记录术语与关键决策。本文将这些思路应用于上传需求文档后的对齐过程；具体实现方式尚未确定。

### 阶段二：Agent 复述需求与用户确认

**目标**：讨论对齐后，由 Agent 复述需求，让用户判断 Agent 是否已经理解自己的需求。

**主要行为**：

1. Agent 用清晰、完整的表述向用户复述需求。
2. 用户检查复述是否准确，指出遗漏、误解或需要调整的内容。
3. 用户确认没有问题后，进入下一阶段。
4. 用户认为存在问题时，返回阶段一继续讨论，并在讨论后再次复述。

**阶段产出**：经用户确认的需求描述。

**通过条件**：用户明确确认 Agent 的需求复述没有问题。

### 阶段三：用户对受影响现有功能的理解考察

**目标**：考察用户对当前需求所影响的现有功能的了解程度，帮助用户理解本次需求与已有功能的关系。

**考察方向**：

- 受当前需求影响的现有功能的用途、操作流程和业务规则。
- 这些现有功能与当前需求的关系，以及本次需求将如何影响它们。

**考察边界**：不考察用户对代码、技术实现或编程知识的掌握程度。Agent 可以读取代码和项目资料来了解现有功能，但面向用户的问题应围绕功能与业务行为。

**主要行为**：

1. Agent 根据已确认的需求和项目上下文，识别受影响的现有功能，并围绕这些功能对用户进行考察。
2. Agent 对考察结果评分。
3. 用户达到 80 分后，完成本阶段并进入下一阶段。
4. 未达到通过分数时，继续本阶段；具体的讲解、补充学习和再次考察机制待定义。

**阶段产出**：用户的考察结果与得分。

**通过条件**：用户得分达到 80 分。

**待确认**：评分满分、评分维度、题型、题量及重试规则。目前尚未确定；若采用百分制，通过条件为得分不低于 80 分。

### 阶段四：HTML UI/UX 设计稿与审核

**目标**：基于当前项目已有页面进行新增或改动，在后续实现前，让用户通过可交互的 HTML UI/UX 设计稿体验并审核界面、操作流程和交互反馈。

**输入**：经用户确认的需求、当前项目已有页面及其布局、组件、样式与交互，以及前面阶段获得的相关项目上下文。

**主要行为**：

1. Agent 先查看当前项目已有页面，了解相关功能的页面结构、视觉风格和交互方式。
2. 在已有页面基础上，按需求新增页面或修改现有页面，生成可交互的 HTML UI/UX 设计稿，支持需求涉及的主要操作、流程跳转和状态反馈。
3. 延续并优先复用项目已有的布局、组件、配色、字体、间距及交互习惯，使新增和改动部分与现有产品保持一致。
4. 可以使用 impeccable skill 约束设计风格和质量，防止设计偏离现有项目；使用时以当前项目的设计规范和已有页面为依据。
5. 用户实际操作设计稿，审核界面与使用体验，并提出修改建议。
6. Agent 根据反馈修改设计稿，再交由用户体验和审核。
7. 重复审核与修改，直至用户确认通过。

**阶段产出**：用户审核通过的可交互 HTML UI/UX 设计稿。

**通过条件**：用户明确确认设计稿通过。

**后续流转**：审核通过后，进入阶段五，生成 spec 与 tickets。

### 阶段五：生成 spec 与 tickets

**目标**：把已经确认的需求和设计稿转化为明确的实现规格与可执行任务，并存放在项目中。

**输入**：经用户确认的需求、审核通过的 HTML UI/UX 设计稿，以及相关项目上下文和前序讨论结论。

**主要行为**：

1. Agent 根据已确认的内容生成 spec，记录需求目标、范围、业务规则、设计要求、实现决策与验收标准。
2. 对仍然缺失或互相矛盾的信息，回到相关阶段澄清，不把未经确认的推测写成既定需求。
3. 根据 spec 拆分 tickets，每个 ticket 明确目标、实现范围、依赖关系与验收标准，并关联对应 spec 和相关设计稿。
4. 优先按可独立演示、验证的完整功能切片拆分任务，控制单个任务的规模，明确执行顺序及阻塞关系。
5. 将 spec 与 tickets 保存为项目内的文档，供后续实现、审查和验收读取。

**阶段产出**：项目内的 spec 文档和 tickets 文档。

**通过条件**：spec 与 tickets 已落盘，内容与确认后的需求及设计稿一致，任务范围、依赖和验收标准足以支持开始实现。

**实现参考**：

- [AI Hero：The to-spec skill](https://www.aihero.dev/skills-to-spec)。
- [AI Hero：The to-tickets skill](https://www.aihero.dev/skills-to-tickets)。

参考文章支持使用本地 Markdown 或外部 tracker。本项目明确要求 spec 与 tickets 存放在项目中；具体目录、命名与文档模板待确定。Agent 根据已确认的需求和设计稿生成后直接进入实现，不增加用户单独审核 spec 或任务拆分的环节。

### 阶段六：使用 implement 实现需求

**目标**：基于 spec、tickets 和设计稿，完成需求实现。

**输入**：项目内的 spec、tickets、审核通过的设计稿，以及已有项目代码和规范。

**主要行为**：

1. Agent 使用 implement 的方式开展实现，读取当前 ticket 及其关联的 spec 和设计稿。
2. 在当前需求对应的独立分支与 Git worktree 中实现，根据该需求内的任务依赖逐项推进，每次聚焦一个范围明确的 ticket；其他需求的 Agent 可在各自 worktree 中同时开发。
3. 围绕可观察的行为实现功能，并进行与改动相适应的测试、类型检查及其他项目检查。
4. 记录各任务的实现进展和验证结果，供后续审查与验收使用。
5. 若发现需求或设计存在缺口，回到相应阶段处理，并同步调整受影响的 spec 和 tickets。

**阶段产出**：需求实现代码、相关测试，以及任务实现和验证记录。

**通过条件**：本次需求涉及的 tickets 已完成实现，相关检查通过，可以进入独立的代码审查与验收阶段。

**实现参考**：[AI Hero：The implement skill](https://www.aihero.dev/skills-implement)。

参考其按单个任务推进和边实现边验证的方式；单个需求内逐项推进不限制多个需求并行开发。本项目将跨模型代码审查与工具验收安排在下一阶段；分支与 worktree 的命名、创建及回收时机、Git 提交及任务状态管理的具体策略待确定。

### 阶段七：跨模型代码审查与工具验收

**目标**：通过不同模型的代码审查和实际工具验收，确认实现满足需求，并留下可核查的验收证据。

**输入**：实现代码、需求、spec、tickets、审核通过的设计稿，以及实现阶段的验证记录。

**代码审查**：

1. 实现完成后，切换到不同于实现阶段的模型执行 code-review；仅开启同一模型的新会话不满足换模型要求。
2. 明确审查范围和代码基准，确保本次实现及后续修复均被覆盖。
3. 参考 code-review 的两个维度，检查代码是否符合项目规范，以及实现是否满足需求与 spec；涉及 UI/UX 时同时对照已通过的设计稿。
4. 审查发现需提供对应代码位置与规范、需求或 spec 依据，以便核查和修复。
5. 对需要修复的问题完成修复及相应复查，记录处理结果。具体严重程度和阻断规则待确定。

**工具验收与证据**：

1. 使用 Playwright 等工具实际运行并验证需求对应的功能、界面与关键交互，逐项对照 spec 和 tickets 的验收标准。
2. 验收成功必须有证据，可采用图片、视频或验收文档中的一种或多种形式。
3. 证据必须来自实际执行的验收过程，并能关联到对应验收项；验收文档应记录执行步骤、预期结果、实际结果与通过或失败结论。
4. 未执行、失败或缺少证据的验收项不能标记为通过。验收失败后修复，并重新执行受影响的验收项，保留复验结果和证据。
5. 保存代码审查报告、问题处理记录、验收结果和证据，作为交付材料。

**阶段产出**：跨模型代码审查报告、问题处理记录、工具验收结果，以及图片、视频或验收文档等证据。

**通过条件**：代码审查达到通过标准，需要修复的问题已处理；需求范围内的验收项通过，且有对应的实际验收证据。

**实现参考**：[AI Hero：The code-review skill](https://www.aihero.dev/skills-code-review)。

参考文章强调从独立上下文进行审查，并分别检查规范符合性与需求符合性；使用不同模型审查是本项目额外明确的要求。具体模型选择、审查通过标准、验收运行环境及证据保存位置待确定。

## 4. 阶段推进原则

- **并行开发优先**：允许用户同时提出多个需求，并让它们独立进入和推进流程；并行支持是项目的基础要求。
- 保持七步流程简洁，在支持并行需求的基础上完成从需求到交付的主线，不额外增加审核阶段或复杂机制。
- 每个需求内部按顺序推进：需求讨论 → 用户判断 Agent 的需求复述是否准确 → 用户对受影响现有功能的理解考察 → 可交互 HTML UI/UX 设计稿审核 → 生成项目内 spec 与 tickets → implement 实现 → 跨模型 code-review 与工具验收。
- 不同需求之间可并行，分别管理上下文、进度和产出；通过独立分支与 Git worktree 隔离代码改动，单个需求的等待或失败不阻塞其他无依赖需求。
- 需求复述和设计稿审核均需要用户明确确认通过。
- 用户对受影响现有功能的理解考察需要达到 80 分的门槛，不考察代码或技术实现。
- 需求复述存在问题时，返回讨论阶段；设计稿存在问题时，继续修改和审核。
- UI/UX 设计基于当前项目已有页面新增或改动，延续现有视觉风格与交互习惯，可使用 impeccable skill 约束风格和质量。
- 实现依据已确认的需求、设计稿、spec 与 tickets；发生变更时，同步调整受影响的材料和任务。
- 代码审查必须使用不同于实现阶段的模型。
- 审查或验收未通过时，进入修复与复查、复验流程；验收成功必须附带实际执行产生的证据。
- 各阶段使用前面已经确认的需求与结论，保持上下文连续；交付材料应能关联需求、设计稿、spec、tickets、实现结果和验收证据。

3. **设计稿标准**：HTML 设计稿需要覆盖哪些页面、状态和交互，用户如何预览及提交反馈？
4. **需求变更处理**：需求确认或考察通过后发生变化，哪些阶段需要重新进行？
5. **文档与任务管理**：spec 与 tickets 的目录、命名、模板及基本状态如何组织？
6. **并行执行与集成策略**：多需求如何调度，worktree 与分支何时创建和回收，如何分配预览端口及隔离测试数据，以及如何处理需求间依赖、合并冲突与集成验证？
7. **跨模型审查规则**：实现和审查分别使用哪些模型，问题如何分级，达到什么标准可以通过审查？
8. **验收与证据管理**：Playwright 等工具如何运行，验收环境如何准备，证据存放在哪里，以及如何关联具体实现版本？
9. **最终交付形式**：如何简洁地向用户呈现代码、设计稿、spec、tickets、审查报告和验收证据？

这些问题暂不阻塞项目目标的记录，将在后续讨论中逐步明确。
