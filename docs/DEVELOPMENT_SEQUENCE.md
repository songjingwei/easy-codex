> 产品目标、流程与阶段通过条件以 [项目目标](PROJECT_GOALS.md) 为准；框架、部署形态与 Agent 选型以 [技术栈](TECH_STACK.md) 为准。

## 1. 开发方式

Easy Codex 不做大而全的首版实现。每次只实现一个可验证切片，确认它能独立运行、演示或测试后，再进入下一个切片。

- **小切片优先**：每个切片只解决一个明确问题，不提前实现后续能力。
- **先做最小可运行路径**：先让一个需求从上传走到最小交付，再逐步补齐七步流程。
- **不提前创建用不到的模块**：packages、页面、抽象和工具都按当前切片需要创建；出现真实复用需求后再抽象。
- **每个切片都有验证方式**：自动化测试、手动验证或端到端场景至少具备一种。
- **未通过不进入下一切片**：切片失败时先修复或缩小范围，不继续堆叠功能。
- **并行需求是产品能力，不是开发方式**：开发仍按切片推进；多需求并行在单需求闭环稳定后实现。

### Git 仓库维护原则

Git 仓库是 Easy Codex 读取项目上下文、生成产物和执行代码改动的核心来源，必须谨慎维护：

- 只在用户授权的仓库和目录内读取、写入和执行命令。
- 记录仓库路径、分支、worktree、产物目录和所有权，避免误操作用户已有改动。
- spec/tickets、设计稿、审查报告和验收证据写入约定目录，不覆盖用户文件。
- worktree/branch 由平台创建并登记，清理前确认归属和未合并改动。
- 默认不执行破坏性 Git 操作；提交、合并、回滚策略需单独确认。
- 并行需求使用独立 worktree，但仍需处理集成冲突和验证结果。

## 3. 切片明细

### 切片 1：样例与验证仓库

目标：准备后续所有验证使用的真实项目样例。

只做：

- 选择或创建一个小型 Git 仓库 fixture。
- 确认 fixture 是独立 Git 仓库，包含可安全验证的初始状态。
- 准备一份 Markdown 需求文档。
- 记录运行项目测试或开发服务器所需的最少命令。

不做：

- 不接入 Agent。
- 不设计完整项目结构。

验证：

- 可以在 fixture 仓库中手动或脚本化运行基础检查。

完成标志：

- 后续切片可以重复使用同一个项目样例和需求样例。
- 默认 fixture：`fixtures/target-app`；默认需求样例：`fixtures/requirements/add-priority-label.md`；验证：`fixtures/scripts/verify.sh`。

### 切片 2：最小工程骨架

目标：建立最小但可演进的工程基础。

只做：

- 初始化 pnpm workspace。
- 配置 TypeScript、ESLint、Prettier、Vitest。
- 创建 `apps/api` 和 `apps/web` 最小入口。
- 创建 `packages/contracts` 共享基础类型。

不做：

- 不创建全部建议目录。
- 不引入 PixiJS、Electron、pi-durable 的完整封装。

验证：

- `pnpm dev` 或拆分命令可以启动 Web 和 API。
- API health check 可用。
- Web 可以引用 `contracts` 类型。

完成标志：

- 工程可以被后续切片稳定扩展。

### 切片 3：API 与数据基础

目标：建立业务数据和 API 基础。

只做：

- Fastify API 基础路由。
- SQLite + Drizzle 初始化。
- 核心表：Project、Requirement、RequirementDocument。
- 文件产物基础目录。
- 记录项目仓库路径、当前分支、工作区状态和所有权信息。

不做：

- 不实现七步状态机。
- 不接入 Agent。

验证：

- API 测试覆盖创建项目、上传需求、查询需求列表。

完成标志：

- 需求文档可以持久化保存并被后续流程引用。

### 切片 4：需求上传与最小 UI

目标：让用户可以在 Web 中提交需求。

只做：

- 项目选择或创建入口。
- Markdown 文件上传。
- 需求列表和需求详情占位页。

不做：

- 不做讨论、设计稿或验收 UI。
- 不做游戏场景。

验证：

- 浏览器中上传 `.md` 后能在列表和详情页看到内容。

完成标志：

- 用户可以从 Web 提交一个需求并查看基本信息。

### 切片 5：事件与阶段状态机

目标：把七步流程固化为可测试的状态机。

只做：

- DomainEvent 模型和单调序号。
- Requirement stage 状态。
- 阶段流转规则和基础通过条件。
- 失败、取消、等待用户状态。

不做：

- 不实现全部 Agent 角色。
- 不实现并行调度。

验证：

- 单元测试覆盖正常流转、退回、失败、取消和恢复。

完成标志：

- 业务后端可以判断当前阶段、合法流转和等待条件。

### 切片 6：Agent 执行最小封装

目标：隔离 pi-durable/pi-ai 细节，先跑通一个会话。

只做：

- `packages/agents` 最小封装。
- pi-ai 模型配置。
- `discuss` 角色会话。
- start、subscribe、cancel、resume 接口。
- 事件适配为统一业务事件。

不做：

- 不实现所有角色。
- 不实现复杂工具权限。
- 不实现多需求调度。

验证：

- 脚本可以对 fixture 仓库启动一次讨论会话。
- 重启后可以恢复会话。

完成标志：

- 业务层可以通过统一接口驱动 Agent 会话。

### 切片 7：阶段一二闭环

目标：完成上传需求到需求确认的最小闭环。

只做：

- 阶段一讨论消息持久化。
- Agent 澄清问题与用户回复。
- 阶段二需求复述。
- 用户确认或退回讨论。

不做：

- 不实现考察、设计稿、spec 和实现。

验证：

- 端到端完成上传 → 讨论 → 复述 → 确认。
- 用户指出问题时可以退回阶段一。

完成标志：

- 一个需求形成经用户确认的需求描述。

### 切片 8：阶段三理解考察

目标：实现受影响现有功能的理解考察。

只做：

- Agent 识别受影响功能。
- 生成业务理解问题。
- 用户作答与评分。
- 80 分通过门槛。

不做：

- 不考察代码或技术实现。
- 不做复杂学习路径。

验证：

- 低于 80 分不能进入阶段四。
- 达到 80 分后可以进入阶段四。

完成标志：

- 考察结果、得分和通过状态可追溯。

### 切片 9：阶段四设计稿

目标：生成并审核可交互 HTML 设计稿。

只做：

- Agent 读取项目已有页面和样式上下文。
- 生成 HTML 设计稿产物。
- 受限 iframe 预览。
- 用户反馈、修改和版本确认。

不做：

- 不追求完整设计系统。
- 不接入 PixiJS 场景。

验证：

- 用户可以实际操作设计稿并提交修改意见。
- 设计稿版本与确认结果关联。

完成标志：

- 用户明确确认某个设计稿版本通过。

### 切片 10：阶段五 spec/tickets

目标：把确认后的需求和设计稿转成项目内文档。

只做：

- 生成 spec 文档。
- 拆分 tickets。
- 写入项目仓库的约定目录。
- 写入前检查目标路径，不覆盖用户已有文件。
- 记录路径、版本和需求关联。

不做：

- 不增加用户审核 spec 的阶段。
- 不实现 ticket 执行。

验证：

- spec 和 tickets 在项目中可读取。
- 内容与确认需求、设计稿一致。

完成标志：

- 实现阶段可以读取明确的任务输入。

### 切片 11：worktree 与实现切片

目标：在隔离工作区中完成一个 ticket。

只做：

- `packages/workspace` 最小 Git/worktree 封装。
- 为需求创建独立分支和 worktree。
- 创建前检查仓库状态，只管理平台创建的分支和 worktree。
- `implement` 角色读取 ticket、spec 和设计稿。
- 完成一个范围明确的 ticket。
- 运行与改动相适应的检查。

不做：

- 不实现多需求并行。
- 不处理复杂合并策略。

验证：

- 代码改动发生在独立 worktree。
- ticket 实现结果和验证记录可查询。

完成标志：

- 一个 ticket 可以被实现并留下验证记录。

### 切片 12：跨模型审查

目标：使用不同于实现阶段的模型审查代码。

只做：

- `review` 角色独立会话。
- 审查范围和代码基准固定。
- 检查规范符合性与需求符合性。
- 输出审查报告。

不做：

- 不实现复杂问题分级流程。
- 不自动合并代码。

验证：

- 审查报告记录实现模型、审查模型、代码基准和问题位置。
- 实现模型与审查模型实际不同。

完成标志：

- 审查结果可以作为交付材料。

### 切片 13：Playwright 验收与证据

目标：用真实工具执行验收并保存证据。

只做：

- `acceptance` 角色或验收任务。
- Playwright 启动项目和执行验收项。
- 保存截图、视频或验收文档。
- 关联需求、验收项、代码版本和执行记录。

不做：

- 不用 Agent 判断替代实际执行结果。
- 不标记缺少证据的验收项通过。

验证：

- 成功验收项有对应证据。
- 失败项可以修复后复验。

完成标志：

- 验收结果可核查、可复验。

### 切片 14：交付视图与单需求闭环

目标：在 Web 中查看完整交付材料。

只做：

- 需求详情页汇总讨论、确认、考察、设计稿、spec/tickets、实现记录、审查报告和验收证据。
- 交付状态展示。

不做：

- 不做游戏场景。
- 不做桌面端。

验证：

- 一个真实需求端到端完成七步流程。
- 每个阶段都有产物和证据。

完成标志：

- 单需求闭环成为后续所有能力的稳定基础。

### 切片 15：双需求并行验证

目标：验证多个需求可以独立推进。

只做：

- 两个需求分别创建 worktree。
- 一个需求等待用户时另一个继续。
- 基础端口和产物目录隔离。

不做：

- 不实现完整调度系统。
- 不处理复杂依赖。

验证：

- 手动或脚本验证两个需求互不污染。

完成标志：

- 并行开发的核心场景成立。

### 切片 16：调度、租约与恢复增强

目标：把并行执行变成可恢复、可管理的系统。

只做：

- 数据库任务队列。
- 任务租约、心跳、超时、取消。
- Worker 崩溃后的恢复核查。
- 需求依赖与 ticket 依赖的基础调度。

不做：

- 不引入 Redis 或独立消息中间件。
- 不做多机调度。

验证：

- 在模型请求、只读工具、副作用工具执行中杀死 Worker。
- 恢复后不会重复副作用或丢失已完成结果。

完成标志：

- 多需求执行具备基础稳定性。

### 切片 17：Electron 最小封装

目标：验证桌面形态可以承载现有系统。

只做：

- Electron main 管理窗口和后台进程。
- preload 暴露受控 API。
- renderer 加载 TanStack Start SPA。
- utility process 承载 Fastify 和 Agent Worker。
- 本机动态端口和启动凭据。

不做：

- 不做完整安装包。
- 不做签名和自动更新。

验证：

- 桌面应用可以运行现有 Web/API/Worker 流程。

完成标志：

- 桌面形态与 Web 形态共享同一业务能力。

### 切片 18：桌面安装包与资源回收

目标：让桌面应用可以分发和稳定退出。

只做：

- 打包生产依赖、pi-durable、pi-ai、SQLite 原生模块。
- 应用退出、更新和崩溃恢复的基础处理。
- Worker、项目服务器和浏览器子进程回收。

不做：

- 不做复杂自动更新策略。
- 不做服务端容器隔离。

验证：

- 在未预装 Node.js 和 Agent CLI 的环境中安装运行。
- 关闭应用后资源被正确回收。

完成标志：

- 桌面端成为可分发的部署形态。

### 切片 19：工作台业务面板完善

目标：让用户不依赖游戏场景也能完成全部流程。

只做：

- 需求列表、阶段详情、讨论、设计稿审核、spec/tickets、审查报告、验收证据面板。
- SSE 事件流和断线回放。
- 键盘操作、可访问名称和错误状态展示。

不做：

- 不做 PixiJS 场景。
- 不追求视觉包装。

验证：

- 用户可以通过 DOM 面板完成七步流程。

完成标志：

### 切片 20：PixiJS 场景原型

目标：验证游戏化场景能表达真实开发状态。

只做：

- 项目、需求、Agent、阶段状态的场景投影。
- 点击对象打开对应业务面板。
- 等待用户、失败、审查通过等状态表达。
- Canvas 失败时仍可使用 DOM 面板。

不做：

- 不做复杂剧情、角色养成或游戏经济。
- 不让动画触发业务状态变化。

验证：

- 多需求切换时场景与业务状态一致。
- 断线重连后场景恢复正确。

完成标志：

- 场景成为参与感表达层，而不是业务状态来源。

### 切片 21：安全、性能与备份硬化

目标：处理交付前的关键风险。

只做：

- 凭据、日志、产物和备份策略。
- 多需求端口、测试数据、浏览器上下文隔离。
- Git 安全检查：worktree/branch 归属清晰，不误删用户改动。
- 性能和资源占用实测。
- 安全检查清单。

不做：

- 不引入复杂权限系统。
- 不做多租户团队权限。

验证：

- 每个风险项有验证记录或明确缓解措施。

## 5. 暂不建议提前投入的方向

- 真正 3D：先用 PixiJS 做 2.5D 场景，只有明确需要三维相机、模型和光照时再引入 Three.js。
- 复杂游戏经济系统：先验证一个需求从提出到验收是否有参与感。
- 自建通用工作流引擎：第一版用数据库任务队列足够。
- 接入 Claude Code/Codex CLI 作为主执行核心：当前方案是 pi-durable + pi-ai，外部 SDK 只作为未来评估项。
- 多机分布式调度：先解决单机多需求并行和恢复。
