# Easy Codex 技术栈

> 状态：技术选型草案，作为后续实现依据；不代表相关能力已经实现。
> 更新日期：2026-11-18。
> 产品定义、流程与阶段以 [项目目标](PROJECT_GOALS.md) 为准。已确定采用 TanStack Start、Electron，以及 pi-durable + pi-ai；其余为本文建议的初始方案。

## 1. 选型目标

### 产品架构：一套 Harness，两种部署

| 层次 | 说明 |
| --- | --- |
| **产品核心** | pi-durable 驱动的 Agent 循环、七步流程编排、worktree 内工具执行、检查点与恢复、审查与验收产物 |
| **工作台** | TanStack Start + 游戏场景（PixiJS）+ DOM 业务面板；与部署形态无关的同一套前端 |
| **部署形态** | **桌面**：Electron + utility process 承载 Fastify 与 Agent Worker；**服务端**：Node 进程 + 按需求隔离的执行环境。协议、API 与业务流程共用，仅进程模型、凭据与沙箱策略不同 |

技术选型服务于 **同一套 Agent harness 与工作台**，同时支持桌面应用与服务端部署，允许多个需求独立推进讨论、设计、实现、审查和验收。技术栈需要满足：

- 同一套工作台在浏览器与桌面应用中运行。
- Agent 能在指定 Git worktree 中读取、修改、运行和验证项目。
- 多个需求拥有独立的上下文、任务、运行环境与交付材料。
- 长任务不依赖页面连接存活；等待用户确认时释放活动执行资源。
- 重启后可以恢复流程和 Agent 执行记录，并核查中断工具的实际执行结果。
- 实现与代码审查使用不同模型，验收结果关联真实执行证据。

工作台、桌面宿主、业务服务与 Agent 集成统一采用 TypeScript。前端以 PixiJS 游戏场景表现开发流程（见 [项目目标](PROJECT_GOALS.md) 的产品定义与游戏体验方向），TanStack Start 承载路由、页面与 React 交互层；主界面不采用常规看板。Electron 与服务端 Node 分别作为两种 **部署 profile** 拉起相同的后台入口与业务包；pi-durable 负责 Agent 执行与检查点，pi-ai 负责多模型接入，业务后端负责七步流程与阶段通过条件。

## 3. 前端：TanStack Start

### 3.1 使用方式

使用 TanStack Start 构建统一工作台，复用 React 页面、路由、组件和数据访问代码；根据部署形态提供两种构建配置。

| 形态 | 构建与运行方式 | 数据访问 |
| --- | --- | --- |
| Web | TanStack Start Node.js 服务，按页面需要选择 SSR 或客户端渲染 | 通过同源 `/api` 访问 Fastify |
| 桌面 | TanStack Start SPA 模式，静态资源随 Electron 分发 | 通过经过认证的本机 HTTP 接口访问 Fastify |

Start 的 SPA 模式会预渲染根路由，生成应用壳；桌面共享页面不得依赖运行时 server functions、server routes 或仅在服务器执行的数据加载代码。

根路由预渲染阶段不访问 Electron 桥接接口、本机后台或用户凭据。平台环境初始化在客户端启动后完成。

### 3.2 与后端的边界

TanStack Start 负责页面与 Web 请求入口；Fastify 是业务 API 的统一实现。需求创建、阶段确认、任务调度和运行记录等逻辑放在共享业务包中，由 Fastify 调用。

Web 专属的页面会话处理可放在 Start 服务端，但不在 Start 与 Fastify 中分别实现一套需求业务逻辑。Web 部署通过反向代理将 `/api` 交给 Fastify，其余页面请求交给 Start。

前端通过统一 API 客户端访问业务能力，分别注入 Web 同源地址或桌面本机地址。模型密钥、pi-durable 和 pi-ai 不进入前端构建产物。

### 3.3 以游戏场景表现开发流程

主界面采用可交互的游戏场景，让用户探索项目、提出建设目标、参与决策，与 Agent 协作并体验交付成果。游戏化界面承载 [项目目标](PROJECT_GOALS.md) 中的参与感目标；Agent 能力与七步流程以产品定义为准。

前端同时支持两类场景变化：执行活动随实时状态变化，已确认的项目成果形成可回访的长期记录。具体建筑、装饰与解锁玩法尚未确定，先验证一个需求从想法到交付的完整体验。

场景语义与业务实体保持明确关联，初始建议如下；具体世界观、美术风格、角色与建筑造型待交互设计确定。

| 业务实体或状态 | 场景表达建议 | 可执行操作 |
| --- | --- | --- |
| 项目 | 一个可探索的工作场景 | 切换项目、查看整体活动 |
| 需求 | 可独立选中的任务对象或区域 | 查看目标、当前阶段与产物 |
| Agent 执行实例 | 关联需求的角色或工作装置 | 查看当前活动、日志与取消入口 |
| 七步流程 | 对应阶段的区域、设施或对象状态 | 打开当前阶段所需的交互 |
| 等待用户 | 对应对象的明确提示 | 回复问题、确认需求或审核设计稿 |
| 失败与阻塞 | 带原因的状态标记 | 查看原因、修复或重试 |
| 审查与验收通过 | 对应产物的完成反馈 | 查看报告、截图、视频和交付材料 |

场景同时呈现多个需求的真实阶段与活动。角色只在执行实例处于活动状态时表现为工作中；没有可量化总工作量时展示阶段和当前动作，不用动画推算完成百分比。

必要操作提供直接选中、快捷入口和键盘操作，不强制用户操纵角色走到某个位置才能确认需求。场景移动和过渡动画不增加业务等待，也不改变产品规定的阶段通过条件。

### 3.4 2D、2.5D 与真正 3D 的边界

PixiJS 主要是 2D 渲染引擎。第一版建议以精灵、层级排序、等距投影、视差与透视网格构建有纵深的 2.5D 场景。透视变形不等于完整三维场景，也不能把支持 WebGL/WebGPU 等同于已经提供三维相机、模型和光照系统。

如果交互设计需要自由旋转三维相机、立体模型或真实光照，再引入 Three.js，并在实现前验证与 PixiJS 的渲染分层、输入命中、坐标映射与资源生命周期。初期不默认让两个引擎共享同一个图形上下文；只有 2.5D 需求时不额外引入 3D 引擎。

### 3.5 PixiJS 与 React 的分工

- PixiJS 负责场景对象、精灵、镜头、指针交互与逐帧动画，使用 `@pixi/react` 集成 React。
- React DOM 负责文字输入、对话、Markdown、代码 diff、设置表单、确认按钮和验收详情，保证文本选择、输入法、键盘与可访问性。
- 游戏场景只在客户端加载与初始化，Start 的预渲染和 SSR 不访问 Canvas、浏览器图形 API 或桌面桥接。
- 高频位置、插值和粒子更新在 Pixi ticker 与场景对象内完成，不在每帧触发 React 状态更新。
- 路由离开、项目切换与应用关闭时释放 ticker、监听器与图形资源，并按资源所有权处理共享纹理，避免重复初始化和泄漏。

### 3.6 业务状态驱动场景

后端保存权威业务状态，前端将需求、执行和事件投影为场景对象。TanStack Query 保存接口数据；场景状态保存镜头、选中对象与动画，不复制一套可以独立推进的业务状态机。

用户点击对象产生业务命令，后端校验并提交结果，事件再驱动场景变化。动画完成、角色抵达、粒子播放结束都不能直接将 ticket 或阶段标记为完成。

事件按持久化序号处理，断线后恢复快照并按需回放；先恢复当前业务状态，再播放必要反馈，不要求重新播放全部历史动画。乱序、重复事件和失败请求不能让场景表现领先于实际结果。

项目成长的场景反馈根据已确认的业务成果生成，保留来源与版本，不根据在线时长、动画循环或模型输出长度推算。存在长期场景布局、装饰或收藏机制时，其记录作为独立的产品状态持久化，并与业务阶段分开管理；镜头、音量与减少动态效果等个人偏好单独保存。尚未确定的玩法不提前建立复杂的经济或奖励系统。

### 3.7 性能、访问与内容预览

- 初期以兼容性较广的 WebGL 为基线，WebGPU 在锁定版本与目标环境验证后按需启用。
- 按需加载场景资源，使用纹理图集、可见区域裁剪和对象复用；限制分辨率、设备像素比与特效开销。
- 应用隐藏或窗口最小化时暂停无必要渲染与动画，后台 Agent 任务继续运行。支持减少动态效果与低画质设置。
- 交互对象提供可读名称和 DOM 对应入口，状态不能只依靠颜色或动画区分。图形初始化失败时仍能访问待处理事项与必要操作。
- 聊天与执行输出增量展示，长列表按需虚拟化；Markdown 限制 HTML，代码查看与 diff 使用独立组件。
- Agent 生成的 HTML 设计稿在独立来源的受限预览环境中运行，不作为游戏场景代码执行，也不接入 Electron preload 桥接。
- 验收截图、视频和 Trace 通过产物接口提供，避免把大文件放入消息正文。

## 4. 桌面端：Electron

### 4.1 进程与职责

Electron 提供统一的 Chromium 页面环境和 Node.js 能力，工作台使用 TanStack Start 的静态构建产物。

- **主进程**：管理窗口、菜单、托盘、文件选择、应用生命周期和后台进程。
- **preload**：通过 `contextBridge` 暴露范围明确的桌面 API，校验 IPC 来源与参数。
- **renderer**：运行 React 工作台，启用上下文隔离与沙箱，不直接访问 Node.js、文件系统或模型凭据。
- **后台 utility process**：承载 Fastify 与独立 Agent Worker；主进程只负责管理，不执行长时间 Agent 任务。

桌面和服务端复用后台入口与业务包，分别由 Electron utility process 和普通 Node.js 进程启动。utility process 的 Node.js 能力不等于操作系统沙箱；项目命令仍需单独约束。

### 4.2 后台连接与资源分发

桌面安装包包含 Electron、工作台静态资源、后台构建产物、pi-durable、pi-ai，以及所需生产依赖。基础 Agent 执行不依赖用户预装 Codex CLI 或 Claude Code CLI。

主进程启动后台，等待就绪信号后通过受控 IPC 向工作台提供连接信息。后台绑定 `127.0.0.1` 的动态端口，使用每次启动生成的凭据认证请求，并校验允许的来源；凭据不写入 URL、日志或浏览器持久存储。

普通业务命令使用 HTTP，实时事件使用可携带认证头的流式请求。Electron IPC 用于桌面能力与连接初始化，不承担第二套业务接口。

静态工作台使用受控应用协议加载，协议处理对齐 Start 的 SPA 壳与深层路由回退。产物与媒体通过受控接口提供；不向预览页面开放工作台凭据或桌面 API。

### 4.3 打包和生命周期要求

- Electron 内置 Node.js 的版本由 Electron 决定，必须验证它满足 pi-durable、SQLite 适配器和其他后台依赖的要求。
- 按目标平台处理原生模块、外部可执行文件、ASAR 解包、签名、更新与资源路径。
- 应用退出与更新前停止接收新任务，保存检查点，并回收 Worker、项目服务器和浏览器子进程。
- 后台崩溃后可以重启服务；在确认旧进程停止并核查中断任务前，不转移存储所有权或重复执行副作用。
- Electron 自带 Node.js 不代表用户项目的工具链齐全；接入仓库时检测 Git、项目所需语言运行时、包管理器和浏览器依赖。
- Playwright 验收所需浏览器单独管理，不假定 Electron 自带 Chromium 可以直接替代所有验收环境。

选择 Electron 是为了简化 TypeScript 后台与桌面集成，代价是较大的基础包体和内存。完整安装包与多需求运行时的资源占用仍需实测。

## 5. 后端：Fastify 与独立 Worker

### 5.1 业务服务

Fastify 提供统一 API，负责项目与需求管理、讨论记录、阶段确认、任务查询、事件回放和产物访问。HTTP 请求将长任务写入数据库并返回任务标识，不在请求生命周期内执行完整 Agent 任务。

前端断开连接或切换需求不终止后台执行；显式取消操作由任务服务处理，并保留已完成步骤与实际退出结果。

### 5.2 Worker 与存储所有权

Worker 在独立进程中运行 pi-durable。第一版按需求分配独立的 Agent 存储，每份存储只允许一个 Worker 写入；该 Worker 内可管理该需求的多个角色会话。

pi-durable 当前要求同一存储由单进程写入，且不提供跨进程写入锁。业务队列的租约只能协调派发，不能单独阻止失去租约的旧进程继续写入。转移所有权前必须停止并确认旧 Worker 退出；无法确认时保持阻塞状态，不能让第二个进程打开该存储写入。

调度器支持并发上限、需求与 ticket 依赖、模型额度、超时、心跳和取消。等待用户回复或审核时，保存业务与 Agent 状态，释放模型请求和工具进程；没有活动子任务时可关闭 harness 与 Worker，后续重新打开存储并恢复。

第一版使用数据库任务队列和租约领取，不引入 Redis 或独立消息中间件。领取、续租和完成操作需要在事务中校验所有权；租约过期的任务进入恢复核查，不能直接当作尚未执行。

## 6. Agent：pi-durable + pi-ai

### 6.1 执行核心与模型接入

使用 **pi-durable（`@earendil-works/pi-durable`）** 构建平台自己的 Agent 执行层，通过 **pi-ai（`@earendil-works/pi-ai`）** 接入多个模型服务商。

pi-durable 提供 Agent 循环、持久化任务、检查点、会话与基础编码工具；pi-ai 统一模型请求与流式响应。平台实现角色指令、上下文组织、权限规则、项目工具、子任务组织和业务事件适配。

这条路线使用模型服务商 API，不直接复用 Claude Code 或 Codex CLI 的完整编码行为。模型相同也不能假定效果相同，必须用真实仓库任务验证完成率、上下文处理和工具可靠性。

### 6.2 各阶段分工

| 阶段 | 默认执行方式 | 平台负责的约束 |
| --- | --- | --- |
| 需求讨论、复述与理解考察 | pi-durable 独立角色会话 | 保存共识、确认和评分依据；阶段通过条件由服务端检查 |
| HTML 设计稿 | pi-durable + CodingTools + 受限预览环境 | 关联设计稿版本与用户确认 |
| spec 与 tickets | pi-durable + 文档工具与产物校验 | 文档写入仓库，校验依赖和验收标准 |
| 实现与修复 | pi-durable + CodingTools + worktree | 控制任务范围，记录变更与验证结果 |
| 独立代码审查 | 同一执行核心，使用不同模型与独立会话 | 固定需求材料和代码基准，默认限制写入 |
| 工具验收 | Playwright 执行任务；Agent 可生成或调整验收脚本 | 保存真实执行结果和证据，核对验收项覆盖情况 |

角色不要求常驻进程。用户确认后生成结构化阶段产物，后续角色读取这些产物和必要代码上下文。审查使用独立上下文，避免直接延续实现会话。

子 Agent 与需求间依赖由平台组织，不能把 pi-durable 的任务能力视为已经实现完整的多 Agent 调度产品。

### 6.3 模型选择与跨模型审查

实现模型与审查模型通过 pi-ai 分别配置，不需要为跨模型审查引入第二套 Agent SDK。

- 每次执行保存 pi-durable/pi-ai 版本、模型服务商、实际模型标识、配置摘要、需求版本、代码基准与会话标识。
- 实现模型从 pi-ai 当前支持且通过项目验证的模型中选择；具体标识在接入时确认。
- Anthropic 审查模型初始建议使用 `claude-opus-5-5`，接入时验证账号、适配器与部署环境可用性。
- 审查前校验实际模型与实现模型不同；仅更换会话、角色指令、服务商代理地址或模型别名不满足跨模型要求。
- 使用了模型路由或回退时记录可核实的实际模型；无法核实是否不同则不能将该次运行认定为满足跨模型审查要求。
- 审查模型不可用时保留等待或失败状态，不能跳过审查并标记交付通过。

### 6.4 工具、中断与恢复

使用 pi-durable 的 CodingTools 提供 `read`、`write`、`edit`、`bash`，并扩展 Git、开发服务器、产物和 Playwright 等平台工具。工作目录固定到对应需求的 worktree，环境变量按执行实例配置。

pi-durable 在任务步骤记录检查点。工具调用中断后，只有明确声明可安全重放的工具才允许自动重跑；其他工具向模型报告中断及已保存的输出，由平台和 Agent 核查实际结果。

只读工具可在确认行为后声明安全重放；Git 提交、安装依赖、启动进程、写文件和外部服务调用等默认按有副作用处理。重放策略必须依据实际行为，不能仅按工具名称判断。检查点不保证外部操作恰好执行一次。

完整恢复需要同时保留 Agent 存储、项目工作区、产物与执行环境信息。任务恢复后核查仍存活的子进程、代码状态和已发生的副作用，再决定继续、修复或请求输入。

### 6.5 应用边界与权限

将 pi-durable 封装在项目内部的 Agent 服务接口后，覆盖启动、继续、订阅事件、取消和读取执行结果。前端消费统一事件，不直接依赖 harness 的内部事件结构。

平台按角色配置工具权限：讨论与审查以读取为主，实现允许在指定工作区修改代码，验收允许启动项目和浏览器。工具权限、命令约束与路径校验由平台实现，并结合操作系统或容器隔离。

模型凭据保存在宿主的受保护环境中，只注入需要的模型客户端；普通项目命令默认不继承模型密钥。第三方仓库内容作为项目数据处理，不能自行扩大执行权限。

Playwright 是验收的实际执行工具。Agent 的判断不能代替执行结果，证据必须关联需求、验收项、代码版本与实际运行记录。

### 6.6 实验性依赖的管理

pi-durable 官方明确说明 API 可能无预告变化。首版将版本和存储格式一起管理，升级前备份存储，验证打开旧记录、恢复任务、取消、工具重放与多会话行为。

先验证代表性开发任务与恢复场景，再扩展功能。Claude Agent SDK 可作为未来评估其他编码运行时的候选，不作为初始依赖；把外部 SDK 包装成一个 durable 工具，只能获得外层任务边界的恢复能力，不能自动恢复 SDK 内部每一步。

## 7. 七步流程与持久化

业务后端管理产品阶段与用户确认，pi-durable 管理一次 Agent 执行内部的任务与检查点。业务阶段对应产品文档的七步；平台运行状态至少区分排队、运行、等待用户、成功、失败、取消和待恢复核查。

阶段流转在业务数据库事务中执行，校验当前阶段、产物版本和通过条件。例如设计稿确认关联明确的设计版本；后续设计发生变化时，由变更规则决定哪些产物和确认需要重新生成。

业务数据库保存需求、消息记录、确认、设计版本、spec、tickets、依赖、执行索引、审查结果、验收项和产物索引。Agent 对话与检查点保存在 pi-durable 存储，两者通过稳定的需求 ID、执行 ID、会话 ID 和提交请求 ID 关联。

两个存储不共享事务。任务派发采用持久化派发记录、稳定请求 ID 与结果对账；重复提交沿用原请求 ID，并在启动时核查已提交但未回写的执行。不能把业务队列重试直接变成新的 Agent 请求。

业务事件使用单调递增序号，先持久化再发布，前端断线后按序号回放。需要逐条回放的 Agent 增量事件同样先保存，再转成客户端事件；高频日志与大输出可保存在独立日志存储中。

第一版复用 pi-durable 的 Agent 恢复能力，不再自建一套模型/工具检查点系统。业务流程仍由平台负责；出现跨机器大量调度、复杂超时与补偿需求时，再评估通用工作流引擎。

## 8. 数据与产物存储

### 8.1 数据库

桌面和单机服务的业务数据采用 SQLite，使用 WAL、短事务与受控写入；团队共享、多服务实例部署采用 PostgreSQL。使用 Drizzle 定义业务数据访问和迁移，分别维护两种数据库的迁移与兼容验证。

Agent 执行数据初期使用 pi-durable 自己的 SQLite 存储，不由 Drizzle 修改内部 schema。业务数据库切换到 PostgreSQL 不会自动迁移 Agent 存储，也不会取消其单进程所有权限制。

服务端 Agent 存储与 worktree 使用可持久化卷，任务恢复时挂载到新的唯一所有者。跨机器调度需要另外解决存储访问和所有权交接；不能让多个 Worker 共享同一 Agent 存储并同时写入。

spec 与 tickets 按产品要求写入项目仓库，业务数据库记录路径、版本及需求关联。关键状态不只存在聊天文本中。

### 8.2 文件产物

HTML 设计稿、截图、视频、Playwright Trace 和完整日志存放在本地目录或对象存储，数据库记录元数据。产物按项目、需求、执行实例和版本组织，并记录内容校验值，避免旧证据被后续执行覆盖。

桌面应用数据写入用户数据目录，不写入安装包或 ASAR。API 凭据使用操作系统保护的凭据存储或服务端秘密管理机制，不写入仓库、任务正文和产物。

## 9. 并行执行与项目环境

Git 操作首先使用 Git CLI，由平台统一创建和回收分支与 worktree。每个活动需求分配独立目录、预览端口、临时目录、浏览器上下文与测试数据命名空间，并记录实际占用情况。

worktree 隔离文件工作区，不隔离进程、网络、凭据或外部数据库。服务端使用独立执行容器补充运行隔离；桌面第一版采用独立进程与权限约束，不宣称已达到容器级隔离。

多个需求通过不同的 Agent 存储与 Worker 并行。同一需求的写入型 tickets 按依赖执行；审查会话对固定代码快照开展工作，避免实现继续修改导致审查范围漂移。

仓库级的分支创建、集成与清理操作需要协调；合并后运行集成检查。最终合并与交付策略仍由产品规则进一步明确，不能只凭各需求在各自 worktree 中通过测试就宣布集成通过。

## 10. 建议工程结构

```text
easy-codex/
  apps/
    web/                    # TanStack Start；Web 与桌面 SPA 两种构建
    api/                    # Fastify API 与 SSE
    worker/                 # pi-durable harness 与工具任务入口
    desktop/                # Electron main、preload、后台启动与打包配置
  packages/
    domain/                 # 需求、阶段、确认、依赖与通过条件
    application/            # 业务用例、任务派发与执行结果对账
    contracts/              # API、事件与结构化产物 schema
    api-client/             # Web/桌面共用的 HTTP 与流式客户端
    agents/                 # pi-durable 封装、pi-ai 配置与角色上下文
    tools/                  # CodingTools 策略与项目专属工具
    workspace/              # Git、worktree、端口与进程管理
    persistence/            # 业务 Drizzle schema、查询与迁移
    artifacts/              # 文件产物存取与索引
    ui/                     # 共享 React DOM 组件与场景内业务面板
    scene/                  # PixiJS 场景、业务状态投影、输入与动画
  docs/
    PROJECT_GOALS.md
    TECH_STACK.md
```

这是建议结构，按实际功能逐步创建；尚无复用需求的模块可以先保留在对应应用内。领域与应用逻辑不直接依赖 Electron、React 或 pi-durable 的内部类型。

## 11. 实施前需要验证的组合

以下验证用于确认选型组合可用，不增加产品的用户审核阶段：

1. **Start + Electron**：桌面 SPA 壳、深层路由、静态资源、preload 初始化和本机认证事件流能够运行。
2. **桌面后台分发**：在未预装 Node.js 和 Agent CLI 的干净环境中，安装包能运行 Fastify、pi-durable 与 SQLite，执行一次 Agent 任务并完整回收进程。
3. **真实开发任务**：使用选定模型完成一个包含项目分析、修改与测试的功能切片，核查工具行为与交付质量。
4. **多需求与等待**：两个 worktree 并行执行互不污染，一个等待用户时另一个继续；关闭并重开等待需求后可以继续会话。
5. **崩溃与交接**：分别在模型请求、只读工具和副作用工具执行中杀死 Worker，验证恢复行为；确认存储不会出现两个写入者。
6. **跨存储对账**：在派发、提交与结果回写之间中断，确认恢复不会产生重复 Agent 请求或丢失已完成结果。
7. **跨模型审查**：通过 pi-ai 使用不同模型审查同一代码版本，记录实际模型与代码基准。
8. **验收闭环**：启动项目、执行 Playwright、保存并展示证据；失败和缺少证据时不会被标记通过。
9. **场景与业务一致性**：多需求切换、乱序与重复事件、断线重连、任务失败时，场景与实际状态一致；动画结束不触发业务通过。
10. **图形与交互**：验证场景命中、镜头、DOM 面板、输入法、键盘操作、资源释放和后台降帧；如引入真正 3D，额外验证两个引擎的协作。
11. **参与乐趣**：用一个需求贯通提出想法、讨论决策、设计体验、并行执行、验收与成果回访，观察用户是否理解自己的影响、愿意继续探索，并能直接找到下一项操作。通过真实试用和反馈验证，不能用画面测试或动画数量替代。

平台自身的场景测试同时覆盖状态投影的自动化验证、Playwright 指针与键盘交互，以及固定视口、固定场景数据、关闭随机动画后的画面验证，不能只检查 Canvas 元素存在。

Electron、PixiJS、pi-durable 与具体数据库适配器的组合需要完成上述验证。精确 API、平台支持与打包依赖以实现时锁定版本为准。
